Every product is emitted once, carrying its facts on `data-*` attributes; search, category, filters and sort then hide/show and re-order those same nodes. That means the card markup has exactly one definition (no JS template duplicating it), the page is complete before JS runs, and swapping in server-driven pagination later replaces `applyShop()` rather than the cards. The cart lines read their prices off those same cards, so a cart total can never disagree with the grid. 4. THE CART IS REAL BUT LOCAL, AND SHARED WITH THE PRODUCT PAGE. Doc 13 wants quantity control, per-business grouping and a live total, and all of that is honest to build client-side. The storage shape lives in static/js/cartflow-cart.js because /product/{slug} writes to the same cart — two pages inventing their own line shape is how a cart loses items. What it will NOT do is pretend to check out: `POST /api/checkout` does not exist, there is no payments integration and no `orders` table, so the checkout button says so instead of faking a receipt. Same rule for Save (doc 12 §19) — device-local, and the copy says so rather than implying the account synced. NO INLINE HANDLERS ON GENERATED MARKUP. Every JS-built row (cart lines) uses `data-*` + one delegated listener. An entity-escaped apostrophe (`'`) is decoded by the HTML parser BEFORE the JS compiles, so a name like "Chef's Special" written into an inline `onclick` would end the string literal early. The server-rendered cards may use `data-*` too — one convention, no exceptions to remember. Section order follows doc 12 §3: search → categories → filters → Recommended → Trending → Discounts → Newest → the full grid.
